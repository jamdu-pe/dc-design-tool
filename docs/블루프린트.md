# 데이터센터 M&E 인프라 설계 TOOL — 블루프린트

> AI 가속기(GPU/TPU/Trainium) 기반 서버·랙을 입력하면, 기계·전기·통신(M&E) 인프라 용량과 자재·제조사를 "레고처럼" 조합해 산출하는 에이전트형 컨설팅 도구.
> 작성일: 2026-08-05 · 대상 실행환경: Claude Code

---

## 0. 한 줄 결론

**가능하다.** 이 문제는 본질적으로 "부품 카탈로그 + 인터페이스 규칙 + 부하계산 엔진 + 규격 검증 + 산출물 생성"의 조합이며, 레고형 조립(모듈 합성)과 에이전트 오케스트레이션에 매우 잘 맞는다. 핵심은 화려한 AI가 아니라 **정확한 부품 스키마와 검증 가능한 계산식**이다. AI(에이전트)는 요구사항 해석, 부품 선정 추론, 규격 대조, 보고서 생성을 담당하고, 숫자는 결정론적 파이썬 엔진이 계산해 신뢰성을 확보한다.

## 1. 왜 "레고"가 성립하는가 — 계층과 인터페이스

데이터센터는 물리적으로 명확한 포함관계(containment hierarchy)를 갖는다. 각 계층을 표준 인터페이스(전력/발열/물리치수/네트워크포트)를 가진 블록으로 정의하면, 상위 블록은 하위 블록의 인터페이스만 알면 조립된다.

```
칩(Chip) → 노드/서버(Node) → 랙(Rack) → 열/포드(Row/Pod) → 홀(Hall/White Space) → 건물(Building)
                                     │
                          [각 계층이 노출하는 인터페이스]
                          - 전력  : 정격/피크 kW, 역률, 전압
                          - 발열  : 총 kW, 액냉 비율, 공급수온(TCS)
                          - 물리  : U/치수/중량(바닥하중)
                          - 통신  : 포트 수/속도/매체(NVLink/scale-out)
```

이 인터페이스가 곧 "레고 돌기(스터드)"다. 블록끼리는 인터페이스 호환성만 맞으면 결합되고, 엔진은 계층을 따라 부하를 누적·변환한다.

### M&E 3대 도메인이 소비하는 인터페이스

| 도메인 | 입력 인터페이스 | 산출(설계) 대상 |
|---|---|---|
| 기계(M) | 발열 kW, 액냉비율, 공급수온, ASHRAE 등급 | CDU/RDHx/CRAH, 칠러, 냉각탑/드라이쿨러, 펌프·배관, 유량, PUE |
| 전기(E) | 정격/피크 kW, 역률, 이중화등급 | 버스웨이/PDU/RPP, UPS(또는 DRUPS), 발전기, 변압기, MV/LV 배전, 배터리 자립시간 |
| 통신(ICT) | GPU/노드 수, 포트속도, 패브릭 토폴로지 | 리프-스파인 스위치, 트랜시버·케이블 BOM, 구조화배선(TIA-942), DCIM/BMS/EPMS, 통신실(MDA/IDA/HDA) |

## 2. 현시점 기준 데이터 앵커 (엔진 검증용 골든값)

카탈로그의 정확성이 도구의 생명이다. 아래는 2025~2026 공개 자료 기준 앵커값이며, 이 값들을 **회귀 테스트(golden test)**로 고정해 엔진 오류를 잡는다. (사양은 벤더 확정 전 추정 포함 → 카탈로그에 `confidence` 필드로 표기)

| 랙 시스템 | GPU/칩 | 랙 전력밀도(대략) | 냉각 | 시기 |
|---|---|---|---|---|
| NVIDIA GB200 NVL72 | 72× Blackwell | 약 120~130 kW/랙 | 액냉(direct-to-chip) 필수 | 양산 중 |
| NVIDIA GB300 NVL72 | 72× Blackwell Ultra | 약 130~150 kW/랙(추정) | 액냉 | 2025~ |
| NVIDIA Vera Rubin NVL144 | Rubin | 약 최대 600 kW/랙(로드맵) | 액냉·고밀도 | 2026 하반기 |
| NVIDIA Rubin Ultra NVL576(Kyber) | Rubin Ultra | 600 kW↑(비공개) | 액냉 | 2027 하반기 |
| Google TPU v7 "Ironwood" | TPU | 포드 단위(액냉) | 액냉 | 2025~ |
| AWS Trainium3 | Trainium | 랙/UltraServer(액냉 지향) | 액냉 | 2026 |

핵심 시사점: 랙 밀도가 GB300 ~130kW에서 Rubin 세대 ~600kW로 약 4~5배 도약한다. **설계 제약의 병목이 "칩 확보"가 아니라 "전력공급·액냉 인프라"로 이동**한다. 따라서 도구의 가치는 이 병목을 정량화하는 데 있다.

> 데이터 유지보수 원칙: 사양은 자주 바뀐다. 카탈로그는 코드가 아니라 `data/` 아래 YAML로 분리하고, 각 항목에 `source_url`, `as_of_date`, `confidence(measured/vendor/projected)`를 필수로 둔다. 신제품 출시 시 YAML 한 줄 추가로 확장(= 레고 블록 추가)한다.

## 3. 시스템 아키텍처 (4계층)

```
┌─────────────────────────────────────────────────────────────┐
│  L4. 에이전트 계층 (Claude Code)                              │
│   오케스트레이터 + 서브에이전트(intake/M/E/ICT/compliance/BOM)│
├─────────────────────────────────────────────────────────────┤
│  L3. 계산 엔진 (결정론적 Python)                              │
│   부하 누적 · 냉각/전력/공간/네트워크 사이징 · 이중화         │
├─────────────────────────────────────────────────────────────┤
│  L2. 규칙/규격 (Rules as data)                               │
│   ASHRAE TC9.9 · Uptime Tier · TIA-942 · IEC/NEC · 유량식     │
├─────────────────────────────────────────────────────────────┤
│  L1. 부품 카탈로그 (레고 블록, YAML)                         │
│   chips · nodes · racks · cooling · electrical · network      │
└─────────────────────────────────────────────────────────────┘
```

**설계 철학: "숫자는 코드가, 판단은 에이전트가."** 용량 계산·이중화·유량 같은 수치는 반드시 파이썬 엔진이 계산(테스트로 검증)하고, LLM은 요구사항 해석·부품 선정 후보 압축·규격 해설·보고서 문장화만 담당한다. LLM이 곱셈을 하지 않게 하는 것이 신뢰성의 핵심이다.

## 4. 계산 엔진 파이프라인 (핵심 로직)

```
[1] 요구사항 정규화
    입력: 목표 IT부하(MW) 또는 목표 랙수/성능, Tier, 기후(외기), 부지제약
        ↓
[2] IT 부하 산정 (Chip→Node→Rack)
    선택 칩 × 수량 → 노드 TDP → 랙 kW → 랙수 → 총 IT부하
        ↓
[3] 기계(냉각) 사이징
    발열 = IT부하 → 액냉/공냉 분배(예: GB200 ~85% 액냉)
    유량 Q(L/min) = 열량(kW) / (ρ·c·ΔT)  → CDU/RDHx 대수, 칠러 톤수, 펌프
    ASHRAE 수온등급(W17~W45), 접근온도, PUE, 이중화(N+1/N+2)
        ↓
[4] 전기 사이징
    랙 kW → 버스웨이/PDU → UPS(kVA = kW/PF, 효율·이중화 2N/N+1)
    → 배터리/플라이휠 자립시간 → 발전기(냉각+하우스부하 포함)
    → 변압기/수전(MV) → 고조파·수용률 반영
        ↓
[5] 공간·구조
    랙수 → 열 배치 → 화이트스페이스 면적 → 바닥하중(kg/m²) → 층고
        ↓
[6] 네트워크(ICT)
    GPU수 → NVLink 도메인 + scale-out 포트 → leaf/spine 대수
    → 트랜시버·MPO 트렁크·DAC/AOC BOM → DCIM/BMS/EPMS 포인트
    → 구조화배선(MDA/IDA/HDA/EDA), 경로/공간
        ↓
[7] 규격 검증
    Uptime Tier · TIA-942 Rated · ASHRAE envelope · 국내전기설비규정
        ↓
[8] 산출물 생성
    설계기준서(Word) · 부하계산+BOM(Excel) · 블록/단선도 · PUE/TCO 추정
```

### 대표 계산식(엔진에 하드코딩·테스트)
- 냉각 유량: `Q[L/min] = P[kW] × 60 / (4.186 × ΔT[K])` (물 기준, ρc≈4.186 kJ/L·K)
- UPS 용량: `S[kVA] = P_IT[kW] × (1+설계여유) / PF / η`
- 발전기: `P_gen = P_IT + P_cooling + P_house + 기동여유` (냉각부하가 IT의 30~50% 지배)
- 화이트스페이스: `A ≈ 랙수 × (랙풋프린트 + 통로배분)` + 전기/기계실 계수
- PUE(추정): `PUE = (IT + 냉각 + 손실) / IT`, 액냉 도입 시 1.1~1.3 목표

## 5. 레고 조립(합성) 방식

부품은 공통 스키마를 가진 YAML 블록. 조립은 **그래프 솔버**가 담당한다.

```yaml
# 예: 하나의 "칩" 블록
- id: nvidia_gb200_superchip
  type: chip
  vendor: NVIDIA
  interface:
    power_kw_typical: 2.7      # superchip(2 GPU+1 CPU) 급 개략
    power_kw_peak: 3.0
    cooling: liquid_d2c        # direct-to-chip 액냉
    liquid_fraction: 0.85
  as_of_date: 2025-11
  confidence: vendor
  source_url: "..."
```

조립 규칙(예): `rack.cooling == liquid` 인데 선택된 `cdu`가 없으면 → 검증 실패 & 에이전트가 CDU 후보 제안. 이렇게 **인터페이스 불일치를 컴파일 타임 오류처럼 잡는 것**이 레고형의 실익이다.

산출은 항상 "구성 트리(configuration tree) + 부하 롤업 + BOM + 검증 리포트" 4종 세트.

## 6. 에이전트 계층 설계 (Claude Code)

오케스트레이터가 아래 서브에이전트를 순차/병렬 호출한다. 각 서브에이전트는 **엔진 함수를 호출(툴 사용)**하고 결과를 해설한다.

| 서브에이전트 | 역할 | 주 호출 |
|---|---|---|
| `intake` | 자연어 요구사항 → 정규 spec.yaml | 파싱/질의 |
| `sizing` | 칩·랙 선택 → IT부하·랙수 | engine.it_load |
| `mechanical` | 냉각계통 사이징·자재선정 | engine.cooling |
| `electrical` | 전력체계 사이징·자재선정 | engine.power |
| `ict` | 네트워크·배선·DCIM | engine.network |
| `compliance` | Tier/TIA-942/ASHRAE 대조 | rules.check |
| `reporter` | 설계기준서·BOM·다이어그램 | xlsx/docx/mermaid |

실행 형태 2가지: (a) CLI 배치(`dc-design build --spec spec.yaml`), (b) 대화형(Claude Code에서 "GB200 5MW, Tier III, 부산 기후로 설계해줘" → 오케스트레이터가 파이프라인 구동).

## 7. 산출물(Deliverables) 정의

1. **설계기준서(Design Basis, .docx)** — 전제·기준·이중화·계산근거 서술.
2. **부하계산 & BOM(.xlsx)** — 칩→건물 부하 롤업, 장비 리스트(모델/제조사/수량/용량), 이중화 반영.
3. **블록 다이어그램/단선도 개요(mermaid→이미지)** — 전력·냉각·네트워크 계통 개념도.
4. **비교 시나리오** — 칩 세대/이중화/냉각방식 바꿔가며 CAPEX·PUE·면적 비교표.
5. **검증 리포트** — 규격 위반·인터페이스 불일치·가정 목록.

## 8. 단계별 로드맵

- **MVP(1~2주)**: 칩 3종(GB200/TPU v7/Trainium3) + 랙 + 냉각/전력 최소 카탈로그, 엔진 부하계산, Excel BOM 출력, GB200 NVL72 골든테스트 통과.
- **v1(3~5주)**: 이중화(N+1/2N), 규격 검증, ICT 네트워크·배선, Word 설계기준서, 서브에이전트 완성.
- **v2**: 다이어그램 자동생성, TCO/PUE 비교엔진, 신제품 카탈로그 확장, (선택) MCP 서버화로 다른 에이전트에서 호출.

## 9. 리스크와 대응

- **사양 불확실성(특히 미출시 칩)** → `confidence` 표기 + 추정치 범위(min/typ/max), 출처·기준일 명시.
- **국내 규격/전기설비기준 반영** → 규칙을 데이터로 분리해 관할 규정(KEC 등) 교체 가능하게.
- **LLM 수치 오류** → 계산은 100% 엔진, 골든테스트·단위테스트 필수. 에이전트는 숫자를 생성하지 않고 인용만.
- **책임 한계** → 산출물은 개념설계·타당성 검토 수준이며 실시설계·인허가는 면허기술자 검토 필요임을 보고서에 명시.

## 10. 성공 기준(Acceptance)

1. `spec.yaml` 입력 시 3종 산출물이 오류 없이 생성된다.
2. GB200 NVL72 1랙 입력 → 랙부하 120~130kW, 액냉유량·UPS·발전기 값이 골든테스트 오차범위 내.
3. 카탈로그에 YAML 블록 추가만으로 신규 칩/장비가 계산에 반영된다(코드 수정 불필요).
4. 이중화 등급 변경 시 전력/냉각 장비 수량이 규칙대로 자동 변동.
5. 검증 리포트가 인터페이스 불일치·규격 위반을 정확히 지적한다.
